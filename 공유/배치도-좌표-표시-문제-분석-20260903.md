## 2. 좌표 표시 문제 — 직접 원인 (HIGH)

### 2-1. B/C/D동 좌표 라벨·툴팁 전멸 (가장 유력)
미커밋 변경이 `gridLabels` 메모를 **A동 전용 논리좌표(X=1~9, Y=1~21)** 로 재작성했는데, 동(dong) 분기 없이 전 동에서 실행됩니다.

- `getColCenterX`는 A-L 라인 존만 필터(lineMap 1~9 → 라인 6·5·4·3·2·1)
- `getRowCenterY`도 A-L7/L6~L1만 계산 → **dong='B/C/D'에서는 모든 후보가 0**
- 결과: 열·행 라벨 루프가 전부 `continue`, `coordOf`는 빈 맵 → 화면 좌표 헤더·툴팁 '좌표 N-M' 모두 사라짐
- 커밋된 HEAD 버전은 `computeGridCoords`(픽셀 클러스터링) 공통 경로라 B/C/D에도 정상 생성됐음 — **diff에서 해당 공통 경로가 삭제됨**
- 증거: `product-display.tsx:1889~2013` (특히 1902~1946), uncommitted diff 347~486행

### 2-2. A동 행(Y) 좌표 라벨 겹침·소실
새 `getRowCenterY`가 "라인 스트립 평균 y"로 행 좌표를 계산하는데, A동 L1~L6 라인은 전부 **세로 컬럼**(동일 y범위 48~732)입니다.

- row3~row8(=L6~L1)의 중심이 **전부 같은 값(~407)으로 수렴** → 좌·우 행 라벨 '3'~'8' 6장이 **같은 위치에 겹쳐 렌더**
- row9~21은 L1 상단 위로 38px씩 투영 → **음수 영역(y<0)으로 밀려 화면 밖 소실**
- 증거: `product-display.tsx:1914~1946`(getRowCenterY), 1956~1963(라벨 루프), 417~479(A동 라인=세로 컬럼 생성)

### 2-3. coordOf — 슬롯 단위 구분 불가 (좌표 규칙 붕괴)
같은 밴드 근접 알고리즘 때문에 `coordOf`가 **한 라인 내 슬롯을 구분하지 못합니다.**

- A-L1 슬롯 1~14 대부분이 Y=2(통로 밴드) 또는 Y=3(중앙 밴드)으로 뭉침, 상단 슬롯만 Y=9로 튐
- 예: 규칙상 `6-17`이어야 할 L3-17 슬롯이 `6-9`로 표시되는 식 — **인접 슬롯이 같은 좌표를 공유하거나 좌표가 튐**
- 결과: 화면 툴팁·호버 좌표로 특정 칸을 지정할 수 없어 **"좌표(열-행)로만 칸을 부른다"는 8/31 규칙이 성립 불가**
- 증거: `product-display.tsx:1974~2012`, 4894~4915(coordOf 주입), 3924~3926(툴팁)

### 2-4. A동 좌표 체계 2중화 (경로별 상충)
같은 A동 칸에 대해 좌표 체계가 **경로별로 분열**되어 있습니다.

| 경로 | 좌표계 |
|---|---|
| A동 단일 화면 (gridLabels.coordOf) | 신규 논리좌표 X=1~9(라인 매핑) / Y=1~21 |
| 총괄 미니맵·검색 결과 (coordOfAll) | 구 computeGridCoords 픽셀 클러스터링 |
| 엑셀 export | 자체 구 클러스터링 재계산 |
| 좌표입력 이동 | 구 좌표계 해석 (1~6열) |

- 예: A-L1 슬롯 5가 화면에서 `9-2`, 검색/총괄에서 `11-5`처럼 **서로 다른 좌표로 표시**
- 좌표입력이동은 화면에 보이는 9열 좌표를 입력하면 "범위 밖(1~6)"으로 거부 (`tsx:2720~2777`)
- 22fd6f2의 '열-행 통일'은 **문자열 순서만** 통일했고 값 체계는 그대로 분열

### 2-5. B/C/D동 위치번호 전멸
자동부여(`computeDongLocMap`, `DONG_LOC_START` 등)를 삭제하고 저장값(`storedLocNos`)만 읽도록 바꿨는데, **B/C/D동 존은 빌더가 locNo를 부여한 적이 없어 저장값 자체가 없습니다.**

- → `dongLocNos = {}` → 칸 표시·모바일·미니맵·엑셀 위치번호 전부 공백/0
- "수기 지정값"을 공급할 데이터 소스(엑셀/마스터 맵)가 B/C/D에는 연결되지 않은 **반쪽 마이그레이션**
- 증거: `tsx:1882~1883`, 5608~5613, 610~622; diff 삭제분(HEAD 5448~5520)

## 3. 데이터 계약 문제 (HIGH/MEDIUM)

### 3-1. 좌표는 어디에도 저장되지 않음 (구조적 구멍)
- payload = 클라이언트가 만든 **존ID 키 배치 맵을 통째로 JSON 블롭** 저장 (`ProductDisplaySnapshot.payload = TextField`)
- v326의 data 키 305개는 전부 존ID/블록명 형식 — **순수 숫자좌표 키 0개**
  - A동 `A-L{line}-{slot}` 115 · B동 한글 존명 `B-B상단-1` 류 42 · C/D동 `R행C열` 137 · 임시칸(`-NEW-*`/`-X`) 11
- 좌표는 프론트가 `zone.style` 픽셀을 매번 클러스터링해 파생하는 **표시 전용 값** — 서버·마스터·차이탭 등 브라우저 외 소비자에게 좌표가 전달되지 않음
- 백엔드 검증도 JSON 유효성·2MB·제품번호 중복 제거뿐 — **칸·좌표·위치번호 규칙 검증 전무** (`views.py:14440~14569`)

### 3-2. 위치번호(locNo) 스키마 3종 혼재
같은 스냅샷 안에 `locNo` 단일값 70칸 / `locNos` 배열 5칸 / **무번호 243칸** (총 318칸).
번호 보유는 **A동 75칸에 한정** — B동 46칸 전체·C/D동 전체·A동 L5~L7에는 번호 필드 자체가 없음.

### 3-3. placement_location_sync.py 잔존 (재오염 위험)
- `sync_placement_locations`는 여전히 `BarcodeMaster.location`을 `'320-A1-1-{위치번호}'`로 **덮어쓰는 파괴적 쓰기**를 보유
- docstring은 "views.py의 `_pd_save_snapshot` 후크에서 자동 실행"·"code-bot 크론 매일 1회"라고 주장하지만, **후크는 2026-08-31에 삭제**되어 주석만 잔존 (`views.py:14516~14518`)
- **크론 스케줄이 살아 있거나 수동 실행 시 마스터 loc이 재오염** (8/31 규칙 정면 위반)
- 다행히 현재는 zone 필드가 `locNo→num`으로 바뀌어 조용히 no-op이 되는 구조적 안전장치 + DB 실측상 마스터 833건이 전산재고와 100% 일치(재오염 없음)

### 3-4. 존ID 화면 노출 폴백 3곳 (8/31 "존ID 표시 금지" 위반 지점)
좌표 매핑 실패 시 raw 존ID가 그대로 노출되는 경로:
1. 검색 결과 `위치 ${dong}동 좌표 ${coordOfAll.get(zone) || zone}` (`tsx:4631`)
2. 셀명/인쇄 `coordOf.get(zoneId) || zoneId` (`tsx:3710`)
3. 검색 hit의 loc `loc: loc || zid` (`tsx:1817`)
- B동·NEW칸·A-X1/X2처럼 coordOf에서 빠지는 존에서 실제 발화
