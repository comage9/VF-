## 2. 수정 전 합의 필요 — "단일 좌표계"의 기준 정의 (P0-P1 착수 전 필수)

v2 §3은 좌표 체계가 "화면 신논리좌표 vs 구클러스터"로 분열됐다고 정확히 지적합니다. 그런데 **"무엇을 기준 좌표계로 할지"는 v2 어디에도 명시되어 있지 않습니다.** 아래 3가지를 결정하지 않으면 P0-2/P0-3/P1 수정이 또 같은 실수를 반복할 위험이 큽니다.

### 결정 1 — A동 좌표 원점·방향
- **현재 설계**(주석 1899~1915): X는 "9=L1, 7=L2, 6=L3, 4=L4, 3=L5, 1=L6", Y는 "8=L1, 7=L2, 6=L3, 5=L4, 4=L5, 3=L6", 하단=1 기준.
- 문제: **물리 배치(Y축 48~732, X축 수평 확장)와 이 논리 Y가 서로 다름** — L1~L6이 세로 컬럼이라 "한 행"이 물리적으로 여러 y에 걸침.
- **결정 필요**: A동 좌표를 (a) 현재 "논리 라인 번호 기반"(슬롯 하단=1, 상단=L7=20) 규칙을 살리되 물리 y와 무관하게 라벨만 고정 배치할지, (b) 물리 그리드(computeGridCoords)로 완전 통일해 B/C/D와 똑같이 할지. → **권고: (a)를 유지하되 "라인/슬롯 → (열,행)"을 단일 맵(하드코딩 대신 데이터)으로 추출**해 화면/검색/엑셀/이동이 같은 맵을 참조. A동은 구조상 클러스터링보다 라인-슬롯 정규화가 정확하므로 computeGridCoords를 A동에 무리하게 적용하지 말 것(세로 컬럼이라 클러스터가 어차피 깨짐).

### 결정 2 — 통로 좌표의 "좌표 부여 대상"
- v2 §2·문제①은 "통로(X=2·5·8)에도 좌표 번호"가 요구라고 합니다. 그런데 **통로에는 칸이 없습니다.** 좌표가 "칸을 가리키는 식별자"라면 통로 좌표의 의미를 명확히 해야 함:
  - (a) 통로는 **라벨/계산상 자리만** 차지(라벨 숫자 2·5·8 표시)하고 배치 대상은 아님 — 칸은 항상 1·3·4·6·7·9열.
  - (b) 통로 바로 옆 칸(A-X1/X2, 일부 특수칸)을 **2·5·8에 스냅**시킴.
- **결정 필요**: ① "통로 좌표 조회 시 무엇이 나와야 하는가"(a면 공백/없음 → 좌표로 지정 불가 경고 표시, b면 인접칸 잡기) → **권고: (a)**. 통로를 "좌표가 존재하는 빈 자리"로 라벨만 그리고, 실제 칸 지정은 1·3·4·6·7·9열로 한정. 그래야 coordToZoneAll 1:1이 깨지지 않음.

### 결정 3 — 다품목 칸의 "번호→품목" 순서 보장 규약
- v2 §4-(c) 실버그의 해법은 **locNos`[i]` ↔ items`[i]` 동기화**를 강제하는 것인데, 현재 locNos 규약(95~96)을 **추가로** 정해야 함:
  - locNos 배열이 **품목 순서와 항상 1:1**(길이 동일)·아니면 **길이가 달라도 "앞에서부터 채움"** 기준 중 무엇인지.
  - 제품 신규 추가 시 번호는 **칸의 max+1**인지 **빈 자리 재사용**인지.
- **결정 필요**: 표시(6378·6400행 `locNos.length===1 ? locNos[0] : locNos[i]`)·범례가 이미 **indexed**(i번째 품목=locNos[i])로 짜여 있으므로 → **권고: 길이 1:1 + 품목 추가/삭제 시 배열을 같은 연산으로 미러링**하는 헬퍼(`syncLocNos(items, locNos)`) 하나를 두고 모든 setData 경로에서 호출. (체인시프트·스왑·드래그·수기편집·보관함 5경로 일괄)

## 3. 수정 시 함께 손봐야 할 비좌표 의존 경로 (간접 파급)

좌표를 "하나"로 고치면 아래가 좌표 문자열에 의존해 함께 깨질 수 있어 **동시 회귀 테스트** 필요:

| 경로 | 좌표 의존 | 비고 |
|---|---|---|
| `persistLocal`/`writeLocalFromPayload`(1386~1392) | payload.data 키=존ID | 좌표가 아니라 **존ID 키**라 안전. 단 sanitize 시 locNos 유지 확인 |
| 엑셀 다운로드(3660~3830) | cellName=좌표 | 좌표 규칙 바뀌면 export row 좌표·`noToZone`(3822) 역방향 즉시 영향 |
| 엑셀 업로드(3763~3821) | cellName→locNo→zone | 유일 좌표 가정 — 중복 시 매핑이 어긋남. §1의 coordToZoneAll 은폐와 같은 위험 |
| 좌표입력 이동(2719~2777) | "가로-세로" 문자열 | 범위 1~6열 하드코딩 — 좌표계 통일 시 여기도 바뀌어야 |
| 검색/정렬(5800, locNoOf) | locNo 문자열 | 76.1% 무번호 칸 검색 불가 — 좌표 표시 복구(P0) 후 재점검 |

## 4. 추가 권고 (P2/P3로 슬쩍 넣을 목록)

1. **`noToZone`(3822)과 `coordToZoneAll`은 별도 맵** — 엑셀 업로드는 locNo(위치번호)로, 좌표이동은 좌표로 찾는데 이 둘을 같은 이름/기능으로 오인하기 쉬움 → 주석·네이밍 구분(P2).
2. **L7 이중 번호(503행 `115+i` vs A_LOCNO_MAP 136~151)** — v2 §7과 같음. 503행 빌드 시 branch 죽이기(P1).
3. **브라우저 육안 검증 항목**(v2 §9-3)을 **기준 좌표 결정(§2) 후** 수행할 것 — 좌표계 기준이 바뀌면 "정상" 판정 기준도 바뀌므로, 합의가 먼저여야 검증 의미가 있음.
