## B. 추가 발견 — 좌표 변환 알고리즘 단위 결함 (선행 문서의 P0/P1과 중첩되나 원인 깊이를 보강)

### B-1. coordToZoneAll이 "좌표 중복"을 은폐 (단일 맵 덮어쓰기)
`coordToZoneAll`(2081~2085행)은 좌표가 겹치는 상황에서 **나중에 순회된 존이 이겨 앞 존은 좌표로 도달 불가**가 됩니다.
```ts
coordOfAll.forEach((coord, zid) => { if (!m.has(coord)) m.set(coord, zid); });
// 첫 존만 기록 — 동일 좌표를 가진 2번째 존은 mapping 자체가 없음
```
- DB 감사에서 "클러스터 충돌 0건"으로 나온 건 **클러스터 결과 좌표가 유일했기 때문**이 아니라, **이 매핑이 앞선 중복을 버려 감춘 결과**일 수 있음.
- 반드시 검증 필요: `coordOfAll`에서 (좌표 → 존 1:N)인 좌표가 실제로 있는지 디버그 출력으로 확인. A동 인접 슬롯이 같은 좌표를 공유한다면(선행 §2-3) 이 맵에서 정확히 1개만 살아남아 **"좌표 검색으로 특정 칸 지정 불가"** 가 됨.

### B-2. A동 좌표 라벨 규칙이 3벌로 중복 구현 (미래 회귀 온상)
동일한 "A동 슬롯 번호 → 행 라벨" 규칙이 **3곳에 각각 별도 구현**되어 있어 한 곳만 고치면 불일치가 생깁니다.
| 위치 | 역할 |
|---|---|
| 2066~2073행 (`gridLabels.rowLabelOf`) | 화면 그리드 라벨 |
| 2736~2746행 (`moveSelectedToCoord.rowLabelOf`) | 좌표입력 이동 해석 |
| 3682~3690행 (엑셀 export `rowLabelOf`) | export 좌표 |
- 세 구현이 현재 **복붙 수준으로 동일**하지만, 앞으로 슬롯 번호 규칙이 바뀔 때(예: A동 확장) 한 곳을 빼먹으면 좌표 체계가 조용히 갈라짐.
- **권장**: 공통 헬퍼(예: `utils.ts`의 `rowLabelOfFor(dong, ri, zones)`)로 단일화한 뒤 세 곳 모두 위임. (B/C/D용 `computeGridCoords`는 이미 공용 함수라 영향 없음)

### B-3. computeGridCoords의 TOL=8px 클러스터링 — 존재하는 행/열 사이의 여백 취급 경계
`computeGridCoords`(326~367행)의 `cluster`는 `v - last > TOL(8px)`로만 새 행/열을 판정합니다. 즉 **간격이 8px 이하로 떨어진 두 칸은 "같은 행"으로 합쳐집니다.**
- 수정 모드의 `ghostCells` 그리드 간격은 `SLOT.h + SLOT.gapY`(≈40px+)라 문제없지만, **사용자가 DnD로 칸을 8px 이내로 겹치게 배치하거나, 새 칸을 기존 칸에 아주 붙여 배치하면** 행/열 클러스터가 병합되어 좌표가 붕괴됨.
- B/C/D동 개별 화면은 1배율 렌더라 안전하나, **줌 확대 상태에서 좌표 계산 시 fitScale과 zoomFactor로 픽셀 좌표를 보정하는지 확인 필요** — 만약 원본 픽셀(보정 전) 기준으로 계산된다면 구역이 클러스터링되어 좌표가 틀어짐. (선행 §환경메모의 브라우저 육안 검증 항목과 연결)
- **권고**: TOL을 좌표 보정 후(또는 논리 그리드 좌표) 기준으로 재정의하고, 병합 대신 "근접하되 다른 칸"은 항상 다른 행/열로 유지.

### B-4. gridCoord 노출이 라벨 체계와 다른 좌표 문자열을 쓸 가능성
- 화면 툴팁(`3924`행)은 `z.gridCoord`를 그대로 표시하고, 그 값은 `gridLabels.coordOf`(=**A동: "9-2"식 논리좌표**)에서 주입(4895행).
- 그러나 같은 화면에서 coordToZoneAll·엑셀(3660행)은 **"col-행"** 을 computeGridCoords 로 계산.
- 툴팁/화면에서 "9-2"로 보이고 검색·엑셀에서 "11-5"로 보이는 **좌표 체계 2중화**(선행 §2-4와 동일)를 **렌더 파이프라인 기준으로 한 번 더 확인**: `ZoneCell`의 `gridCoord` 표시와, 검색결과의 `coordOfAll.get(zone)` 표시가 서로 다른 맵 사용주임. (4631행 참조)
- 이는 단순 표시 불일치를 넘어 **사용자가 화면 좌표로 검색/이동 명령을 줬을 때 실패/오목표**로 이어지므로 P1 우선.

### B-5. dongLocNos 저장값 의존 + 무번호 폴백 — B/C/D/신규칸의 호버 좌표 공백
- 선행 §2-5와 동의하되, 추가 근거: `gridLabels`의 `locOuter`/로케이션 라벨 분기가 `dongLocNos[z.id]` **존재 여부만** 보고 칸 안/밖 표시(2026~2049행)를 결정.
- B동·C동·D동·`-NEW-*`·A-X 칸은 `dongLocNos`에 키가 없어 **아무 로케이션 번호도 렌더되지 않고**, 툴팁엔 좌표 조차 없는 경우 `그리드 좌표 없음 + 제품 정보`만 남음 → 현장에서 "칸을 특정할 표식이 없다"는 불만의 직접 원인.
- 이 칸들에 대한 **좌표 표시 최소 보장**(B/C/D는 computeGridCoords 1:N 중복 허용하되 표시는 항상)이 필요.

### B-6. zombie code 잔존으로 인한 혼선
- `gridCoord?: string` 필드(97행)와 `calcZigzagLocNo`(388행 주석만) 등은 작업본에서 **설정되지만 소비되지 않는/주석화된** 잔재. 검토·수정 시 "이게 실제 동작 좌표인지" 오인할 여지 → P1 작업 때 정리 권장(필드 주석에 "deprecated" 표기 또는 제거).

## C. 검증 단계 제안 (코드 수정 전, 반드시)

1. **coordToZoneAll 중복 좌표 실측**: 개발서버 콘솔에서 `[...coordToZoneAll.keys()]` 길이 vs `coordOfAll.size` 비교. (중복이 있으면 후자 < 전자)
2. **줌 상태 좌표 정합성**: zoomFactor>1 상태에서 특정 칸 툴팁 좌표와 검색 좌표가 같은지 확인.
3. **로컬 브라우저 육안**: `localhost:5174`에서 (a) A동 행 라벨 겹침, (b) B/C/D 좌표 헤더 부재, (c) 무번호 칸 호버 — 3가지를 캡처해 좌표값 기록.
