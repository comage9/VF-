# 작업지시서 — A동 칸(존) 물리 배치 정렬 (opencode 실행)

> 사용자 지시: Hermes가 직접 수정하지 말고 opencode에 위임, Hermes는 재확인 담당.

## 1. 문제 (화면 실측 근거, 2026-09-04 Hermes Playwright 실측)

A동 배치도의 **칸(존) 물리 위치가 논리 좌표와 어긋나 있음**. 로케이션 번호는 좌표 고정(A_COORD_NOS)이라 정상인데, **칸 자체가 엉뚱한 위치에 렌더**되어 사용자 화면에서 "배치된 제품과 로케이션 번호가 불일치"해 보임.

### 실측 데이터

| 항목 | 값 |
|---|---|
| 저장 data (제품→존) | 2031 → A-L4-12, 516 → A-L4-14, 2034 → A-L4-19 등 |
| 저장 layout (존→물리좌표) | A-L4-12 = (left:184, top:238) · A-L4-13 = (left:184, top:200) · **A-L4-14 = (left:288, top:162)** · A-L3-16 = (left:288, top:86) |
| 화면 실측 | **2031 칸이 X4열·(4,16) 위치에 표시 → 번호 65가 붙음** · 516 칸은 X6열(6,18) 부근 다품목 구역에 표시 → 71→72 |
| 문제 본질 | **같은 라인(예: L4)의 존들이 서로 다른 X열(left)에 흩어져 저장됨** — L4-12·L4-13은 left:184, L4-14는 left:288 (X6열 위치) |

→ 즉, layout에 저장된 A동 존들의 style.left/top이 **표준 그리드 좌표를 벗어나 뒤섞인 상태**로 영속화되어 있음. 이전 커밋(97c18b8, 5db2a07)들은 표시(번호)만 고쳤고, **존 위치 자체는 안 고쳐서** 사용자가 계속 "안 맞는다"고 보고.

## 2. 수정 목표

A동 layout에 저장된 존들의 물리 좌표(style.left/top)를 **표준 그리드 좌표로 재계산·재정렬**하여, 화면에서 제품이 지정 좌표에 정확히 놓이게 한다.

- (4,14) 자리에는 2031 → 로케이션 61 표시
- (4,16) 자리에는 516 → 로케이션 65 표시
- 1~151 번호가 카논 좌표와 일치

## 3. 좌표·배치 표준 (반드시 코드에서 확인 후 사용)

- **X열(가로) ↔ 라인**: L1=X9 · L2=X7 · L3=X6 · L4=X4 · L5=X3 · L6=X1 (사용자 확정 카논)
  - 각 X열의 left(px) = 코드의 `A_LINES`/`lineLeftOf`/빌더 기준 (스킬: padL=28, SLOT 48×34)
- **Y행(세로) ↔ 슬롯**: 슬롯 s → Y = s+2 (Y=2 통로). top(px) = 하단 기준 38px 주기 (스킬·`buildGridCoordSystem` 확인)
- **사용자 카논 순서**: ① X9/X7 위→아래(1~38) ② X6/X4 아래→위(39~76) ③ X3/X1 아래→위(77~, (3,3)=77)
- 로케이션 번호는 `A_LOCNO_MAP`/`A_LOCNOS_MAP`/`A_COORD_NOS` — **수정 금지** (이미 올바름)
- 존 ID(예: A-L4-12)는 이 지시서 내부에서만 사용. 사용자·문서에선 좌표로만.

## 4. 작업 범위 (제한)

1. **A동 layout(존 배열)의 물리 좌표 재계산·저장** — 다음 두 곳에 동일하게 반영:
   - 프론트 localStorage 키: `vf_product_display_layout_v1`
   - 서버 스냅샷: `POST /api/product-display` (payload의 `layout` — 현재 최신 version 340)
2. 원인이 코드(빌더/복원/이동 로직)에 있다면 그 지점도 수정하되, **다른 동(B/C/D/E)·기존 기능 회귀 없이**.
3. 다음을 조사해 판단하라: layout이 왜 뒤섞였는가? (a) 과거 칸 이동/수동 조작의 저장 잔재 (b) 복원/빌드 경로 버그 → (a)면 데이터 재정렬로, (b)면 코드 수정으로 해결하고, **저장/복원 시 항상 표준 좌표를 강제하는 방어 코드**를 추가하는 것을 권장.

## 5. 절대 금지 (회귀 방지)

- **제품 배치 data는 절대 변경 금지** (data 맵: 존 id → 제품번호 문자열). 제품이 어느 존에 속하는지는 그대로.
- A_LOCNO_MAP/A_LOCNOS_MAP/A_COORD_NOS 등 번호 기준표 **수정 금지**.
- B/C/D/E동 layout·data **건드리지 말 것**.
- 로케이션 번호 렌더 오버레이(좌표 기준) 로직은 이미 정상 — 불필요한 변경 금지.
- 사용자 확정 좌표(예: 2031=(4,14), 516=(4,16), 2034=(4,19))는 재배치 후에도 유지되어야 함.

## 6. 검증 (실행자가 완료 전 반드시)

1. A동 존들의 left/top이 라인·슬롯 표준과 일치하는지 (각 X열 left가 라인별로 동일값, top이 슬롯 순서대로)
2. 화면 확인: 헤드리스 Playwright 또는 로컬 브라우저로 A동 열어 2031이 (4,14)에 61과 함께, 516이 (4,16)에 65와 함께 표시되는지
3. tsc 에러 0 (사전 존재 TS6133 노이즈 제외) + 빌드 통과
4. 스크린샷 + 변경 요약 + 커밋 (메시지에 실측 검증 명시)

## 8. 실행 제약 (opencode 환경)

- **opencode는 `~/.hermes` 등 외부 디렉토리 접근 권한이 없음** (auto-reject) → 그쪽 파일 참조/읽기 시도 금지.
- 작업 디렉토리는 `/home/comage/vf-project/VF-new` 하나로 한정 (그 안의 공유/, frontend/, backend/ 만 사용).
- 필요한 기준표·좌표·카논은 위 §3과 참고 문서(공유/ 내)에 모두 있음 — 추가 조회 불필요.
- **데이터(layout) 수정은 프론트 localStorage만으로 끝나지 않는다**: 최종 반영은 `POST http://localhost:5176/api/product-display` (body: `{payload: JSON.stringify({data, layout, lineConfig, staging, locExceptions, savedAt}), saved_by: "browser"}`)로 **서버 스냅샷에 저장**해야 사용자 화면에 보인다. (curl 사용 가능)
- layout JSON 구조: localStorage `vf_product_display_layout_v1` (또는 서버 payload의 `layout` 필드) — `{__v, layout: [{key:"A", zones:[{id, num, style:{left,top,width,height}, ...}]}, ...]}`
- A동 존 정렬 시 style.width/height(48×34)는 유지하고 left/top만 표준 좌표로 재계산. 빈칸 포함 모든 존.
- 헤드리스 브라우저(playwright) 사용 가능: `frontend/client`에 `playwright.evidence.config.ts` + 캐시 Chromium(`/home/comage/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome`)이 있다. 실행: `cd frontend/client && npx playwright test --config=playwright.evidence.config.ts e2e/…`
